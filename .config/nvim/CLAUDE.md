# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Overview

This is a Neovim configuration using the built-in plugin manager (`vim.pack`). Each plugin's setup lives in its own file under `plugin/`.

## Architecture

- **init.lua**: leaders, `lua/config/` modules, the colorscheme, the `PackChanged` hook, then `vim.pack.add()` for every plugin. The colorscheme comes first because `vim.pack.add()` raises when a plugin fails to install, which would stop init.lua
- **plugin/<name>.lua**: one file per plugin with its `setup()` call and keymaps. Neovim sources these after init.lua, before each plugin's own `plugin/` files

## Key Configuration Details

- **Leader key**: Space ` ` (set in init.lua)
- **Local leader**: Space ` ` (set in init.lua)
- **Plugin manager**: `vim.pack`, no automatic update checking
- **Default colorscheme**: umber — generated into `colors/` by `~/.config/umber/neovim.py` (never edit the generated files; edit the generator and rebuild). One scheme holds both variants and follows 'background'. If the generated colors are missing, nvim falls back to the built-in habamax.

## Plugin Development

When adding a plugin:
1. Add its URL to the `vim.pack.add()` list in init.lua (`version = ...` only when tracking a branch or a release range)
2. Create `plugin/<name>.lua` with its `setup()` call and keymaps. Skip the file when the plugin sets itself up from its own `plugin/` file with defaults (gitsigns, render-markdown)
3. If the plugin needs a build step, add it to the `PackChanged` autocmd in init.lua, which must stay above `vim.pack.add()`
4. Restart, then commit `nvim-pack-lock.json`

Everything loads at startup. In init.lua `load = false` is already the default and works like `:packadd!`, whose `plugin/` files still load during startup. Only a `load` function that skips `:packadd`, followed by a later `:packadd`, defers a plugin, and the measured startup cost did not justify one.

## File Structure

```
.
├── init.lua              # Entry point, plugin list
├── nvim-pack-lock.json   # Plugin lockfile (vim.pack)
├── plugin/               # One setup file per plugin
├── after/ftplugin/       # Per-filetype settings (buffer-local, after the runtime ftplugins)
├── colors/               # umber, generated by ~/.config/umber/neovim.py
├── lsp/                  # One server config per file (vendored from nvim-lspconfig)
└── lua/
    ├── config/           # options, keymaps, lsp (enable + LspAttach)
    └── lualine/themes/   # umber lualine theme, generated
```

## Plugin Management

- `nvim-pack-lock.json` pins every plugin's revision. A fresh machine installs at those revisions
- `:lua vim.pack.update()` opens a review tab: `:write` applies, `:quit` discards, then `:restart`
- Plugins install to `~/.local/share/nvim/site/pack/core/opt`
- Language servers and formatters come from Homebrew (`~/.config/brew/Brewfile`), not Mason

## LSP Architecture

This config uses the Neovim 0.11+ LSP approach without nvim-lspconfig:
- `lsp/<name>.lua` holds each server's full config (`cmd`, `filetypes`, `root_markers`, settings), vendored from nvim-lspconfig and merged with local overrides. A new server needs its own file here
- `lua/config/lsp.lua` calls `vim.lsp.enable()` and sets buffer keymaps in an `LspAttach` autocmd. Keymaps must not go in a `vim.lsp.config("*")` `on_attach`: a server config with its own `on_attach` replaces it (functions are not merged)
- blink.cmp adds its completion capabilities to `vim.lsp.config("*")` itself

- Kept on purpose: blink.cmp (native completion is weaker on large Kotlin lists), lualine (the umber generator emits its theme), autopairs, every parser and conform entry
- vim.pack facts checked in a sandbox: `vim.pack.add()` in init.lua only adds to 'runtimepath', so config `plugin/` files can call `setup()` and run before each plugin's own `plugin/` file. `version = vim.version.range("1")` checks out the release tag, which blink's binary downloader needs. `PackChanged` must be registered before `vim.pack.add()`. The lazy.nvim clones cannot seed `vim.pack`: they are partial (`--filter=blob:none`) clones, and vim.pack clones a `file://` source in full, which fails because the missing blobs exist only on GitHub (`could not fetch ... from promisor remote`)
- Migration gotcha: nvim-treesitter symlinks `~/.local/share/nvim/site/queries/<lang>` into whichever plugin copy installed the parser, so all 37 pointed into the lazy.nvim clone. `install()` skips installed languages and `:TSUpdate` only re-checks links for languages without a recorded revision, so neither re-links them. Re-point them at the `vim.pack` copy (`site/pack/core/opt/nvim-treesitter/runtime/queries/<lang>`) before deleting `~/.local/share/nvim/lazy`, or every link dangles and highlighting silently stops for all but the seven languages Nvim bundles queries for (c, lua, markdown, markdown_inline, query, vim, vimdoc). A fresh install links to the `vim.pack` copy and needs nothing
- `init.lua` starts with `vim.loader.enable()`. lazy.nvim turned the byte-code cache on implicitly, and without it every `require` compiles from source: startup went from 64.8 to 67.9 ms to 78.6 to 81.2 ms (headless, a Python file, first run excluded). With it, 60.9 to 68.4 ms against lazy.nvim's 61.9 to 64.2 ms in the same session. Deferring fzf-lua's setup was rejected: with the cache on it costs 3.3 to 3.9 ms (setup itself about 0.5 ms, the rest loading the module), down from 8.2 to 8.8 ms

### 2026-10-13: Umber Follows the Appearance
Ghostty switches `umber`/`umber-light` with the macOS appearance, but Neovim always loaded the dark scheme, so under light appearance the light cursor `#a74900` sat 1.04:1 from dark CurSearch and hid there. `colors/umber.lua` and `lua/lualine/themes/umber.lua` now hold both variants and branch on 'background'. The `-light` files are gone. Neovim sets 'background' from the terminal at startup (OSC 11) and again when Ghostty reports an appearance change (DEC 2031). The scheme must never set 'background' itself: a scheme that does makes Neovim delete its update autocmd at VimEnter (`_core/defaults.lua`), and the next change re-sources the scheme, which sets it back, and Neovim drops to its stock colours. `neovim.py` also reads `minimum-contrast` from `ghostty/config` instead of mirroring 2.5 by hand.

### 2026-10-05: CurSearch No Longer Hides the Cursor
`CurSearch` used the cursor colour as its bg. Ghostty's `minimum-contrast = 2.5` also applies to the block cursor, so on a cursor-coloured cell it redrew the cursor pure black (white on light) and the character under it vanished. `neovim.py` now derives CurSearch as a bold ember tile below the cursor in both variants, with slot 15 text, as light as 2.6:1 to the cursor allows (dark `#9f4a12`, light `#431900`), and the audit enforces it. A tile above the cursor on light could only sit 1.32:1 from `Search`, or go lighter than `Search` and sit 1.09:1 from the page. `Todo` lost its fill and is now bold italic amber text, matching the IntelliJ emitter. `@comment.note`/`warning`/`error` (vimdoc `Note:`/`Warning:`/`Deprecated:`, gitcommit breaking change) lost theirs too: bold slots 12/3/9. Warning is bold italic on slot 3 (the `DiagnosticWarn` colour): the slant separates it from vimdoc headings, which share slot 3 bold. Against `Todo` (slot 11 bold italic) only a shade separates it (OKLab dE 0.07), which is acceptable because no installed parser captures `@comment.todo`, so the two never share a buffer. Installing the treesitter `comment` parser would change that. The audit checks cursor contrast on every group with a bg except the four the cursor never sits on (`Cursor`, `Substitute`, the two Telescope titles), so a new fill under 2.5:1 fails the build. Known limitation: Ghostty follows the macOS appearance but nvim always loads dark `umber` (`lazy.lua`), so under light appearance the light cursor `#a74900` sits 1.04:1 from dark CurSearch and still hides there. Making nvim follow the appearance needs one scheme that branches on 'background' and never sets it, because a colorscheme that sets 'background' disables nvim's live updates at VimEnter and is discarded on the next change.
